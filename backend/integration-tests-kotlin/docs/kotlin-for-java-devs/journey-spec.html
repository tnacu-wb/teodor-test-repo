Inside JourneySpec

Every journey extends one base class. This page explains what a scenario inherits from it — identity, stubs, cleanup, and evidence — why a shared base class is the right tool, and the Kotlin features that make the journey DSL work. No Kotlin experience assumed.

1Why this class exists

Journeys run concurrently — up to four specifications, four scenarios each — against shared services and shared WireMock instances. A scenario can only survive that environment if four things are guaranteed, every time:

  • Identity. Each scenario needs a unique testId. Stubs carry it, requests carry it, and cleanup finds scenario-owned state by it. Two scenarios sharing an ID would consume each other's stubs.
  • Scoped stubs. Installed mappings must match only requests from this scenario. The installer stamps the test-ID matcher onto every mapping.
  • Strict cleanup. Scenario-owned mappings and journal events must be removed even when the test fails — otherwise every red run poisons the shared WireMocks for the runs after it.
  • Evidence. When a scenario fails in CI, the triage material — what stubs were installed, what was sent, what came back, what failed — must exist as a file, because nobody can re-run the moment.

JourneySpec owns all four. A journey class declares scenarios and writes only booking data, service calls, and expectations. Everything below the dotted line of "what am I actually testing" is supplied:

suppliedtestId = "get-company-by-id-…-ci6fdr" ← unique per scenario run
suppliedevidence sink → build/test-evidence/<testId>/evidence.txt
you writeinstallFor(booking) ← stubs, auto-scoped to testId
you writeval result = CompanyEntityApi().getCompanyById(id, testId)
you writeexpect("returns the company") { … }
suppliedcleanup: every mapping + journal event owned by testId removed — pass or fail
suppliedevidence file written: PASSED / FAILED + the failure message

The Java instinct here would be a @BeforeEach/@AfterEach pair plus a utilities class. The base-class approach is stronger for the same reason ServiceApiClient is: the lifecycle is not a convention a journey follows, it is the only way a scenario can exist. You cannot declare a scenario without receiving a fresh testId, and you cannot skip cleanup, because both live in code you never write.

2Writing a journey

A journey is a class with no body of its own: it passes a description and a block of scenarios to the JourneySpec constructor. Inside scenario, the helpers below are in scope.

journeys/companyentity/GetCompanyByIdSpec.kt 
class GetCompanyByIdSpec :
    JourneySpec(
        "get company by id",
        {
            scenario("GET /v1/companies/id/{id} returns company when id is a corporate id") {
                val company = Companies.NEILL_TECHNICAL_SERVICES
                val booking = Booking(companies = listOf(company))

                installFor(booking)

                val result =
                    CompanyEntityApi().getCompanyById(
                        id = company.corpId,
                        testId = testId,
                    )

                result.attachEvidence("Get Company By Id")

                expect("returns the company with negotiated rates") {
                    result.response.status.value shouldBe 200
                    result.body.shouldMatch(company)
                }
            }
        },
    )
// The JUnit 5 equivalent. The lifecycle is split across annotations and
// fields; each piece is individually forgettable.
class GetCompanyByIdTest {
    private String testId;
    private EvidenceSink evidence;

    @BeforeEach void setUp() {
        testId = TestIds.newId("get company by id", …);  // forgettable
        evidence = new EvidenceSink(testId);              // forgettable
    }

    @Test void returnsCompany() { /* stubs, call, assertions */ }

    @AfterEach void tearDown() {
        mocks.removeFor(testId);   // forgettable — and must run even on failure
        evidence.write();
    }
}

What is in scope inside a scenario block:

HelperWhat it does

installFor(booking)Installs every default stub the Booking data selects, scoped to testId. Optional excluded drops defaults from the plan. An excluded ID the Booking did not select throws before any WireMock call, naming the plan's actual IDs.
installStub(stub)Installs one self-contained stub, scoped the same way.

4Method walkthrough

The headings below use the exact source names. Each section explains one declared method.

scenario

This is the only method on JourneySpecScope. It registers one Kotest scenario. It creates the test ID, evidence sink, mock installer, and author scope before it runs the author block.

testkit/JourneySpec.kt 
suspend fun scenario(
    name: String,
    test: suspend ScenarioScope.() -> Unit,
) = featureScope.scenario(name) {
    val testId = testIdFor(featureName, name)
    val evidenceSink = ScenarioEvidenceSink(testId)
    val mockInstaller =
        MockInstaller(IntegrationTestConfig.wiremock, evidenceSink)
    val scenarioScope =
        ScenarioScope(testId, mockInstaller, this, evidenceSink)
    var primaryFailure: Throwable? = null
    var outcome = ScenarioEvidenceOutcome.PASSED

    try {
        withContext(HttpEvidenceContext(evidenceSink)) {
            runWithCleanup(
                test = { scenarioScope.test() },
                cleanup = {
                    try {
                        evidenceSink.recordCleanup(mockInstaller.removeFor(testId))
                    } catch (cleanupFailure: CleanupException) {
                        evidenceSink.recordCleanup(cleanupFailure.result)
                        throw cleanupFailure
                    }
                },
            )
        }
    } catch (failure: Throwable) {
        primaryFailure = failure
        outcome = ScenarioEvidenceOutcome.FAILED
        evidenceSink.recordScenarioFailure(failure)
        throw failure
    } finally {
        finalizeScenarioEvidence(evidenceSink, outcome, primaryFailure)
    }
}
void scenario(String name, ScenarioTest test) {
    featureScope.scenario(name, kotestScope -> {
        String testId = testIdFor(featureName, name);
        ScenarioEvidenceSink sink = new ScenarioEvidenceSink(testId);
        MockInstaller mocks = new MockInstaller(wiremock, sink);
        ScenarioScope scope = new ScenarioScope(testId, mocks, kotestScope, sink);
        try {
            runWithCleanup(() -> test.run(scope), () -> sink.recordCleanup(mocks.removeFor(testId)));
        } catch (Throwable failure) {
            sink.recordScenarioFailure(failure);
            throw failure;
        } finally {
            finalizeScenarioEvidence(sink);
        }
    });
}

runWithCleanup always attempts cleanup. A cleanup failure is recorded before it propagates. The outer catch records the final scenario failure and rethrows it. The finally block writes evidence for every outcome. Cancellation also passes through this path as a Throwable. The method records it and rethrows the same value.

installFor

This method forwards the Booking plan to MockInstaller. It supplies the current scope's test ID. The default empty exclusion set keeps the normal call short. Selection validation and WireMock failures propagate to the scenario.

testkit/JourneySpec.kt 
suspend fun installFor(
    booking: Booking,
    excluded: Set<String> = emptySet(),
) {
    mockInstaller.installFor(
        booking = booking,
        testId = testId,
        excluded = excluded,
    )
}
void installFor(Booking booking,
                Set<String> excluded) {
    mockInstaller.installFor(booking, testId, excluded);
}

The method returns Unit. Its effect is remote WireMock registration and evidence. It does not catch failures. The surrounding scenario method owns failure recording and cleanup.

installStub

This method forwards one direct planned stub. It injects the scenario test ID. The installer scopes every mapping before registration and records successful registrations.

testkit/JourneySpec.kt 
suspend fun installStub(stub: PlannedStub) {
    mockInstaller.installStub(stub, testId)
}
void installStub(PlannedStub stub) {
    mockInstaller.installStub(stub, testId);
}

The method returns Unit. It performs no local validation or error handling. Registration failures propagate to scenario.

callCount

This method converts an author-facing Upstream to its WireMockTarget. It asks the installer for the count that matches this test ID.

testkit/JourneySpec.kt 
suspend fun callCount(upstream: Upstream): Int =
    mockInstaller.countCallsFor(upstream.target, testId)
int callCount(Upstream upstream) {
    return mockInstaller.countCallsFor(upstream.target(), testId);
}

The method returns the remote journal count without changing it. It can return zero without prior installation. Admin or protocol failures propagate to the assertion block.

expect

This method gives one assertion block a readable label. withClue adds the label to assertion failures. It can also wrap a non-assertion throwable in an AssertionError.

testkit/JourneySpec.kt 
suspend fun expect(
    name: String,
    block: suspend () -> Unit,
) {
    try {
        withClue(name) { block() }
    } catch (labelled: AssertionError) {
        val cause = labelled.cause
        if (cause is CancellationException &&
            cause !is TimeoutCancellationException
        ) {
            throw cause
        }
        throw labelled
    }
}
void expect(String name, ThrowingBlock block) {
    try {
        withClue(name, block);
    } catch (AssertionError labelled) {
        Throwable cause = labelled.getCause();
        if (cause instanceof CancellationException &&
            !(cause instanceof TimeoutCancellationException)) {
            throw (CancellationException) cause;
        }
        throw labelled;
    }
}

Genuine scenario cancellation is control flow. The method unwraps and rethrows it without a clue label. A timeout is a test finding, so it stays wrapped and labeled. All other assertion failures also keep the label.

attachEvidence

This is a member extension method. Its dispatch receiver is ScenarioScope. Its extension receiver is ApiResult<T>. This combination gives the method access to both the result response and the scenario evidence sink.

testkit/JourneySpec.kt 
fun <T> ApiResult<T>.attachEvidence(prefix: String? = null) {
    evidenceSink.recordHttp(prefix, response.httpEvidence())
}
static <T> void attachEvidence(
        ApiResult<T> result,
        @Nullable String prefix,
        ScenarioEvidenceSink evidenceSink) {
    evidenceSink.recordHttp(prefix, httpEvidence(result.response()));
}

The method returns Unit. A null prefix is valid. The sink creates an unprefixed evidence entry. Response evidence is bounded before the sink records it. Recording failures propagate to scenario.

testIdFor — file-level support function

This function is not a class method. scenario calls it to create a matcher-safe owner ID. It normalizes the feature and scenario names, limits the base to 90 characters, and adds six random lowercase letters or digits.

testkit/JourneySpec.kt 
private fun testIdFor(featureName: String, scenarioName: String): String {
    val base =
        "$featureName $scenarioName"
            .lowercase()
            .replace(Regex("[^a-z0-9]+"), "-")
            .trim('-')
            .take(90)
            .trim('-')
    val suffix =
        (1..6).map { (('a'..'z') + ('0'..'9')).random() }
            .joinToString("")

    return "$base-$suffix"
}
private static String testIdFor(String feature, String scenario) {
    String base = normalizeAndLimit(feature + " " + scenario, 90);
    String suffix = randomLowercaseLettersAndDigits(6);
    return base + "-" + suffix;
}

The random suffix reduces collisions between repeated or concurrent runs. The function does not guarantee deterministic output. It returns a new value on each call.

5The scenario lifecycle

The interesting part is failure handling. scenario(...) wraps your block in this real sequence:

testkit/JourneySpec.kt · testkit/ScenarioLifecycle.kt 
val testId = testIdFor(featureName, name)          // mint identity
val evidenceSink = ScenarioEvidenceSink(testId)     // open the artifact
val mockInstaller = MockInstaller(IntegrationTestConfig.wiremock, evidenceSink)

try {
    withContext(HttpEvidenceContext(evidenceSink)) {  // see the withContext card below
        runWithCleanup(
            test = { scenarioScope.test() },           // your block
            cleanup = { evidenceSink.recordCleanup(mockInstaller.removeFor(testId)) },
        )
    }
} catch (failure: Throwable) {
    evidenceSink.recordScenarioFailure(failure)        // message into evidence.txt
    throw failure
} finally {
    finalizeScenarioEvidence(evidenceSink, outcome, primaryFailure)  // always write the file
}
// The rules runWithCleanup encodes, in Java exception vocabulary:
try {
    test.run();
} catch (Throwable testFailure) {
    try { cleanup.run(); }
    catch (Throwable cleanupFailure) {
        testFailure.addSuppressed(cleanupFailure);   // red test stays the headline
    }
    throw testFailure;
}
cleanup.run();   // green test + failed cleanup → the cleanup failure fails the test

Three rules fall out of that shape, and they are worth knowing when reading a red build:

  • Cleanup always runs, pass or fail. A failing scenario does not leave stubs behind for the next run to trip over.
  • The test failure stays the headline. If cleanup also fails, its exception is attached as suppressed — Java's addSuppressed, same meaning — never replacing the real failure.
  • A green test with failed cleanup is a failure. Leaked WireMock state is a bug even when the assertions passed.

The evidence file is written in the finally, so it exists for every outcome. That file — build/test-evidence/<testId>/evidence.txt — holds the installed stubs, attached HTTP exchanges, cleanup counts, and the failure message. It is the first thing to open when CI is red.

6Kotlin, feature by feature

Each card explains one feature: what it is, the nearest Java concept, and what the code would look like without it. The everyday basics the examples also use — val, default arguments, suspend, nullable types — get one-line Java anchors in the cheat sheet at the end.

abstract + init the class body is registration

an abstract base whose constructor does the wiring; instance initializer block

An init block runs as part of the constructor. JourneySpec uses it to hand your scenario block to Kotest the moment the journey class is instantiated. The consequence reads strangely to Java eyes: a journey class has no methods at all — declaring the class is registering its scenarios. 

abstract class JourneySpec(
    private val description: String,
    body: suspend JourneySpecScope.() -> Unit,
) : FeatureSpec() {
    init {
        feature(description) {
            JourneySpecScope(description, this).body()
        }
    }
}
public abstract class JourneySpec extends FeatureSpec {
    protected JourneySpec(String description, ScenarioBlock body) {
        // same idea: the constructor registers the scenarios with the framework
        feature(description, scope -> body.declare(new JourneySpecScope(description, scope)));
    }
}

suspend T.() -> Unit the DSL-shaped parameter

Consumer<Scope>, but this is the scope, and it may pause at I/O

The body parameter is a suspending lambda with receiver. The receiver type decides what is callable inside the braces: inside the journey block this is a JourneySpecScope, so scenario(...) is in scope; inside a scenario block this is a ScenarioScope, so installFor, expect, and testId are in scope. This is the whole mechanism behind "it looks like a language, but it is just classes": the compiler enforces which helpers exist at which nesting level. 

// the scope type at each level decides the vocabulary:
JourneySpec("get company by id", {        // this: JourneySpecScope
    scenario("…") {                          // this: ScenarioScope
        installFor(booking)                  // resolves on ScenarioScope
        expect("…") { … }
    }
})
// Java's nearest shape — explicit scope variables at every level:
new JourneySpec("get company by id", journey -> {
    journey.scenario("…", scenario -> {
        scenario.installFor(booking);
        scenario.expect("…", () -> { … });
    });
});
Why suspend on the lambda type?

Everything inside a scenario does I/O: installing stubs is an HTTP call, typed clients are suspend functions, callCount queries WireMock. Declaring the block suspend lets scenario code call all of them directly, in plain top-to-bottom style, with no futures and no .join().

infix + name = how the example reads

assertEquals(expected, actual); /* comment */ argument labels

Two small syntaxes make the §2 example read the way it does. First, result.response.status.value shouldBe 200 is an ordinary method call: shouldBe is declared infix, which lets a one-parameter function drop the dot and parentheses. Kotest's matchers use it so assertions read as sentences. Second, getCompanyById(id = company.corpId, testId = testId) uses named arguments: the caller labels each value with its parameter name, checked by the compiler — what Java approximates with /* id= */ comments or a builder. 

// infix — these two lines are the same call:
result.response.status.value shouldBe 200
result.response.status.value.shouldBe(200)

// named arguments — labels are checked by the compiler:
runWithCleanup(test = { scenarioScope.test() }, cleanup = { … })
// the Java shapes these replace:
assertEquals(200, result.response().status().value());

runWithCleanup(/* test= */ () -> scope.test(), /* cleanup= */ () -> { … });
// the comments are unchecked; swap the arguments and it still compiles

by interface delegation

hand-written forwarding methods, generated by the compiler

ScenarioScope declares : TestScope by kotestScope. Read it as: "this class implements TestScope, and every method I do not override forwards to the kotestScope field". One line replaces a page of boilerplate, and it is why scenario blocks can use Kotest utilities directly — the scope you are standing in is a real Kotest TestScope, not a wrapper you must unwrap. 

class ScenarioScope internal constructor(
    val testId: String,
    private val mockInstaller: MockInstaller,
    private val kotestScope: TestScope,
    private val evidenceSink: ScenarioEvidenceSink,
) : TestScope by kotestScope
public final class ScenarioScope implements TestScope {
    private final TestScope kotestScope;
    // … other fields, constructor …

    // then one forwarding method per TestScope member, by hand:
    @Override public TestCase testCase() { return kotestScope.testCase(); }
    @Override public CoroutineScope …    { return kotestScope.…; }
    // …and it silently breaks when TestScope gains a method
}
What breaks without it?

Either ScenarioScope stops being a TestScope — and scenario blocks lose direct access to Kotest's test utilities — or someone maintains the forwarding methods by hand and re-syncs them on every Kotest upgrade. Delegation keeps the compiler responsible for that sync.

withContext coroutine context elements

ThreadLocal-like context that survives thread hops

Scenarios run concurrently — up to four specifications, four scenarios each — each with its own evidence sink. When response decoding deep inside ApiResult needs to record a malformed body, how does it find this scenario's sink without every function passing it along? Java's answer is a ThreadLocal — but coroutines hop threads at every suspension, so a thread-local set on one thread is gone after the next HTTP call. A coroutine context element is the coroutine-safe version: it travels with the coroutine, not the thread. 

// JourneySpec puts the sink into the context for the scenario's duration:
withContext(HttpEvidenceContext(evidenceSink)) {
    runWithCleanup(test = { scenarioScope.test() }, cleanup = { … })
}

// the element is ~4 lines; Key is a companion object — Kotlin's "static" holder:
internal class HttpEvidenceContext(
    val recorder: HttpEvidenceRecorder,
) : AbstractCoroutineContextElement(Key) {
    companion object Key : CoroutineContext.Key<HttpEvidenceContext>
}
// the ThreadLocal shape this replaces — correct only on one thread:
static final ThreadLocal<EvidenceSink> SINK = new ThreadLocal<>();

SINK.set(evidenceSink);
try { test.run(); }
finally { SINK.remove(); }
// breaks silently once the work moves to another thread mid-test

fun T.f() in a class member extension functions

a static helper(result, sink) — but callable only where both exist

attachEvidence is declared inside ScenarioScope as an extension on ApiResult<T>. That gives it two receivers at once: the result it is called on, and the enclosing scope whose evidenceSink it uses. The payoff is precise availability — result.attachEvidence(…) reads naturally, needs no sink argument, and does not compile outside a scenario block, because only there do both receivers exist. 

class ScenarioScope … {
    fun <T> ApiResult<T>.attachEvidence(prefix: String? = null) {
        evidenceSink.recordHttp(prefix, response.httpEvidence())
    }
}

// in a scenario — no sink in sight, the scope supplies it:
result.attachEvidence("Get Company By Id")
// the static-helper shape — caller must fetch and pass the sink:
Evidence.attach(result, evidenceSink, "Get Company By Id");
// nothing stops calling it with the wrong scenario's sink

internal constructor public type, restricted creation

public class with a package-private constructor, module-wide

ScenarioScope's type is public — every journey block has one as its receiver — but its constructor is internal: only this module can create one. That is the point of the whole design: a scenario's identity must be minted by JourneySpec, with a fresh testId, a fresh evidence sink, and cleanup wired in. Code that could build a ScenarioScope by hand could fake all three.
