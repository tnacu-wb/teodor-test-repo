Inside installFor

How a Booking becomes WireMock mappings: selection, leftover checks, ownership stamping, and registration. Each Kotlin keyword in that path is explained against the nearest Java idea. No Kotlin experience assumed.

1Why this function exists

Journeys run concurrently against four shared WireMock instances. A scenario that hand-picks mappings — or forgets to scope them — either misses the call it meant to mock, or silently consumes another scenario's stub. installFor is the one function that turns scenario data into registered mappings, and it does four jobs that must not diverge:

  • Select. Booking describes the world, not one endpoint. One table — defaultStubsFor — decides which logical stubs that world needs.
  • Adjust loudly. excluded may drop entries from that table, but only IDs the Booking actually selected. A typo fails before any WireMock call, naming the plan.
  • Own. Every mapping gets this scenario's wb-test-id matcher stamped on in one place. A builder cannot omit it and leave a mapping that serves traffic but survives cleanup.
  • Register. Each mapping is POSTed to the right WireMock Admin, then recorded as evidence under the stub's ID.

The same MockInstaller.installFor is the local provisioning API's only entry point. A journey and a POST /mock-sessions walk the same path.

you writeBooking(companies = listOf(company))
you writeinstallFor(booking) ← optional excluded
suppliedselectedStubs: defaultStubsFor + unknown-ID check + filterNot
suppliedscopedTo(testId) stamps baggage: wb-test-id=<testId>
suppliedWireMock Admin POST /__admin/mappings (one call per mapping)
suppliedevidence: recordInstalledStub(stub.id, mapping, testId)

The Java instinct is a helper that loops a list of stub builders. That helper would still let you pass an ID the Booking never selected, and still let a builder forget the test-ID matcher. Here both mistakes fail at the compiler's neighbour: a leftover check throws, and ownership is applied after the builder returns.

2Writing a call

Inside a scenario, installFor already knows testId. You pass the Booking and, when the happy-path defaults are wrong for this scenario, the IDs to drop.

scenario("GET /v1/companies/id/{id} returns company when id is a corporate id") {
    val company = Companies.NEILL_TECHNICAL_SERVICES
    val booking = Booking(companies = listOf(company))

    installFor(booking)                          // every default this Booking selects
    // … typed-client call, expect …
}

scenario("an Opera deposit lookup failure returns the OHIP deposit error") {
    val booking = depositBooking(reservationId = "6004304")
    val room = booking.room

    // Exceptional: a downstream rejection cannot coexist as normal Booking world state.
    installFor(booking, excluded = setOf(OPERA_RESERVATION_DEPOSITS_STUB_ID))
    installStub(reservationDepositsOperaFailure(booking, room))
}
// The shape this replaces: pick stubs by hand, stamp ownership by hand.
// Each line is forgettable; an unknown ID is silent.
List<PlannedStub> stubs = defaultStubsFor(booking);
stubs.removeIf(s -> s.id().equals("booking.opera.company-profile-search"));
for (PlannedStub stub : stubs) {
    wiremock.stub(stampTestId(stub, testId));   // forgettable
}

Three author shapes:

CallUse when
installFor(booking)The Booking's defaults are the world this scenario needs.
installFor(booking, excluded = setOf(ID))A default must never reach WireMock. The ID must be one this Booking selected.
installStub(stub)A mapping outside the Booking gates, or a later moment in the journey. Direct install, with the stub's own unique ID.

Overriding a default combines the last two shapes: pass the default's ID in excluded, then installStub the override. The override never reuses the default's ID — every custom or error stub declares its own unique stub ID in the custom.<upstream>.<name> style and lives under stubs/<upstream>/custom, so evidence and cleanup identify it unambiguously. That is why GetReservationsByIdsSpec excludes the GET stub (ID booking.opera.get-reservation) and then installStub(getReservationEmpty(…)), whose ID is opera.get-reservation.empty: the empty variant is a different stub with its own identity.

journeys/ohip/GetReservationsByIdsSpec.kt 
installFor(booking, excluded = setOf(OPERA_RESERVATION_GET_STUB_ID))
installStub(getReservationEmpty(hotelId = booking.hotel.hotelId, reservationId = room.reservationId!!))
installFor(booking, Set.of(OPERA_RESERVATION_GET_STUB_ID));
installStub(getReservationEmpty(booking.hotel().hotelId(), room.reservationId()));

An unknown excluded ID throws IllegalArgumentException before any Admin request, and the message always names This Booking selected: … so you can see the actual plan.

MistakeWhat throws
Exclude an ID the Booking did not selectUnknown stub IDs in excluded

installStub is not checked against the plan. A directly installed stub supplies its own ID and WireMockTarget; only excluded is validated against what the Booking selected.

// MockInstaller — the shared implementation:
suspend fun installFor(
    booking: Booking,
    testId: String,
    excluded: Set<String> = emptySet(),
) {
    val selected = selectedStubs(booking, excluded)

    if (selected.isEmpty()) {
        if (excluded.isEmpty()) {
            evidenceSink?.recordEmptyPlan("Booking", testId)
        } else {
            evidenceSink?.recordFullyExcludedPlan("Booking", excluded, testId)
        }
        return
    }

    for (stub in selected) {
        installStub(stub, testId)
    }
}

An empty Booking is a successful no-op: it records empty-plan evidence and does not talk to WireMock. When exclusions empty a plan that did select stubs, the recorded evidence is a fully-excluded plan instead, naming the excluded IDs. A failed registration is not rolled back at failure time; cleanup later finds whatever did get in by the test-ID matcher, so a partial install is still reclaimed.

What a stub is

Each public stub builder returns one PlannedStub: an ID, a WireMock target, and an ordered list of mappings. The constructor rejects an empty mappings list. Builders return unscoped mappings; installStub stamps ownership just before registration, for both the default path and a direct installStub call.

stubs/PlannedStub.kt · stubs/opera/OperaReservationDepositsStubs.kt 
data class PlannedStub(
    val id: String,
    val target: WireMockTarget,
    val mappings: List<StubMapping>,
)

const val OPERA_RESERVATION_DEPOSITS_STUB_ID = "booking.opera.reservation-deposits"

fun reservationDeposits(booking: Booking, rooms: List<BookingRoom>): PlannedStub =
    PlannedStub(
        id = OPERA_RESERVATION_DEPOSITS_STUB_ID,
        target = WireMockTarget.OPERA,
        mappings = rooms.map { room -> reservationDepositsMapping(booking, room) },
    )
public record PlannedStub(String id, WireMockTarget target, List<StubMapping> mappings) {
    public PlannedStub {
        if (mappings.isEmpty()) throw new IllegalArgumentException(…);
    }
}

Exclude, in place

A deposit Booking selects the reservation-deposits default among its Opera reads. Excluding it drops that one ID and keeps the remaining defaults in order; the override then arrives by installStub, under its own ID:

defaultsopera-reads · opera-amounts · opera-deposits · opera-folios · …
excludedbooking.opera.reservation-deposits ← dropped
installedopera-reads · opera-amounts · opera-folios · … ← order of remaining defaults kept
installStubcustom.opera.reservation-deposits-failure ← own ID, direct install

That algebra is selectedStubs. After the unknown-ID check it is one collection operation: drop excluded IDs.

stubs/DefaultStubs.kt 
fun selectedStubs(
    booking: Booking,
    excluded: Set<String> = emptySet(),
): List<PlannedStub> {
    val defaults = defaultStubsFor(booking)
    val planIds = defaults.mapTo(LinkedHashSet()) { it.id }
    val unknownExcluded = excluded.filterNotTo(LinkedHashSet()) { it in planIds }
    require(unknownExcluded.isEmpty()) {
        "Unknown stub IDs in excluded: $unknownExcluded.\nThis Booking selected: $planIds."
    }
    return defaults.filterNot { it.id in excluded }
}

fun defaultStubsFor(booking: Booking): List<PlannedStub> =
    cdhStubs(booking) +
        worldlineStubs(booking) +
        datatransStubs(booking) +
        aemStubs(booking) +
        operaStubs(booking)
List<PlannedStub> defaults = defaultStubsFor(booking);
Set<String> planIds = defaults.stream()
    .map(PlannedStub::id).collect(toCollection(LinkedHashSet::new));
Set<String> unknownExcluded = excluded.stream()
    .filter(id -> !planIds.contains(id)).collect(toCollection(LinkedHashSet::new));
if (!unknownExcluded.isEmpty()) {
    throw new IllegalArgumentException(
        "Unknown stub IDs in excluded: " + unknownExcluded
            + ".\nThis Booking selected: " + planIds + ".");
}
return defaults.stream()
    .filter(s -> !excluded.contains(s.id()))
    .toList();

Ownership, then Admin

scopedTo copies the stub and overwrites any existing test-ID header matcher, so a directly installed stub that already carried a foreign test ID still belongs to this scenario. Then each mapping is registered in declared order, and evidence is recorded only after WireMock accepts it.

testkit/mocks/MockInstaller.kt 
internal fun PlannedStub.scopedTo(testId: String): PlannedStub =
    copy(
        mappings = mappings.map { mapping ->
            mapping.copy(
                request = mapping.request.copy(
                    headers = mapping.request.headers.orEmpty() +
                        (BAGGAGE_HEADER to testIdHeaderMatcher(testId)),
                ),
            )
        },
    )

internal suspend fun installStub(stub: PlannedStub, testId: String) {
    val scoped = stub.scopedTo(testId)
    for (mapping in scoped.mappings) {
        wiremock[scoped.target].stub(mapping)
        evidenceSink?.recordInstalledStub(scoped.id, mapping, testId)
    }
}
static PlannedStub scopedTo(PlannedStub stub, String testId) {
    List<StubMapping> scoped = new ArrayList<>();
    for (StubMapping mapping : stub.mappings()) {
        Map<String, StringValuePattern> headers =
            new LinkedHashMap<>(mapping.request().headers() == null
                ? Map.of() : mapping.request().headers());
        headers.put(BAGGAGE_HEADER, testIdHeaderMatcher(testId));
        scoped.add(mapping.withRequest(mapping.request().withHeaders(headers)));
    }
    return stub.withMappings(scoped);
}

4Kotlin, feature by feature

Each card explains one feature the install path actually uses: what it is, the nearest Java concept, and — expand the panel — what the code would look like without it. Everyday basics also used here (val, for, if) sit in the cheat sheet.

data class copy

a record, plus a generated wither for every property

A data class is Kotlin's record: equals, hashCode, toString, and component accessors come free. copy(…) is the wither — named arguments name only the fields that change, the rest stay. scopedTo is three nested copies: stub → mapping → request, overlaying the baggage matcher on the headers map. Without copy that would be three hand-written builders. 

stub.copy(mappings = mappings.map { mapping ->
    mapping.copy(request = mapping.request.copy(headers = …))
})
// Java 16+ record: you write the wither (or a builder) yourself
public PlannedStub withMappings(List<StubMapping> mappings) {
    return new PlannedStub(id, target, mappings);
}

fun T.f() extension functions

a static helper(T, …), callable as if it were a method of T

fun PlannedStub.scopedTo(testId: String) is compiled as a static function whose first parameter is the receiver. At the call site it reads stub.scopedTo(testId). Putting ownership on the type, not on a utilities class, is what keeps both install paths — defaults and installStub — on one operation.

What would the code look like without it?

A StubOwnership.scope(stub, testId) helper, and every caller remembering to call it. The extension does not add power; it makes the forgetting shape look wrong, because an unscoped stub going into wiremock.stub no longer has a named verb sitting on it.

= default name = default and named arguments

telescoping overloads; /* name= */ comments, but compiler-checked

excluded defaults to empty, which is why the happy path is installFor(booking). Named arguments let a scenario pass only the exclusion it needs — excluded = setOf(…) — without a builder and without an argument-order trap. The same names are used when ScenarioScope forwards to MockInstaller, so testId cannot be swapped with a string that happened to sit next to it. 

installFor(booking)
installFor(booking, excluded = setOf(OPERA_RESERVATION_GET_STUB_ID))
installStub(getReservationEmpty(hotelId = hotelId, reservationId = reservationId))
installFor(booking);
installFor(booking, Set.of(OPERA_RESERVATION_GET_STUB_ID));
installStub(getReservationEmpty(hotelId, reservationId));
// swap the two strings and it still compiles; nothing names them at the call site

buildList return@ a list builder, and a return that is not the function

new ArrayList<>() + add; a labeled break out of a lambda

defaultStubsFor concatenates one private function per upstream. Each of those functions is a buildList { … } block: Kotlin gives you a mutable list as this and you add(…) into it. The Booking gates live at the top of that block, one visible if / let per stub.

return@buildList exits the lambda, not cdhStubs as a whole — though here they are the same, because the function is that lambda. It is how booking.loggedUser ?: return@buildList stops adding CDH stubs once there is no logged-in user, without nested if (user != null) wrapping the rest of the table. 

private fun cdhStubs(booking: Booking): List<PlannedStub> =
    buildList {
        if (booking.companies.isNotEmpty()) {
            add(companySearch(booking.companies))
        }
        val user = booking.loggedUser ?: return@buildList
        user.companySpend?.let { add(companySpend(user, it)) }
        user.employeeSpend?.let { add(employeeSpend(user, it)) }
        val tetheredAccount = user.tetheredAccount ?: return@buildList
        add(cdhRegistrationDetails(user, tetheredAccount))
        // …
    }
private List<PlannedStub> cdhStubs(Booking booking) {
    List<PlannedStub> stubs = new ArrayList<>();
    if (!booking.companies().isEmpty()) {
        stubs.add(companySearch(booking.companies()));
    }
    User user = booking.loggedUser();
    if (user == null) return stubs;
    if (user.companySpend() != null) stubs.add(companySpend(user, user.companySpend()));
    // …
    return stubs;
}
Why a labeled return, not a plain return?

Inside a lambda, a bare return would return from the enclosing function — here that is the same, but the compiler still wants the label when the lambda is inlined, and the label documents the intent: stop filling this list. Java's equivalent is just return stubs; from the helper, because Java has no non-local return from a lambda.

?. ?: orEmpty

if (x != null); x != null ? x : default; null-to-empty collection

String? is a type that admits null; plain String does not. x?.let { add(…) } runs the block only when x is non-null — that is most of the Booking gates. ?: is Elvis: "this, or else that". orEmpty() turns a nullable list or map into an empty one, which is how scopedTo overlays the baggage matcher onto headers that may not exist yet.

val user = booking.loggedUser ?: return@buildList
mapping.request.headers.orEmpty() + (BAGGAGE_HEADER to matcher)
if (booking.aem() != null && booking.aem().footer() != null) {
    stubs.add(footer(booking.aem().footer()));
}
User user = booking.loggedUser();
if (user == null) return stubs;

require filterNot in

checkArgument-style guard; Stream.filter; contains, but as an operator

require(condition) { message } throws IllegalArgumentException with the lazily built message when the condition is false — Java's if (!ok) throw new IllegalArgumentException(…) in one line. The $unknownExcluded inside the message is a string template: the value is interpolated, no + concatenation. After that guard, selection is one line: filterNot { it.id in excluded } is "drop members whose ID is in the set" — in is contains with the operands flipped. mapTo and filterNotTo are map / filterNot that write straight into the destination collection you pass, here a LinkedHashSet so the error message keeps plan order.

Why not mutate the defaults list?

A mutable pass would mix validation and deletion in one loop, and a later reader could not see that unknown IDs never reach WireMock. The immutable pipeline keeps "throw" before "I/O" as a visible seam: if you are past the require, the plan is legal.

suspend coroutines

CompletableFuture / virtual threads, with blocking-style syntax

Installing a mapping is an HTTP call to WireMock Admin. suspend marks a function that can pause at that I/O without blocking a thread. The code still reads top to bottom. One rule matters day to day: a suspend function can only be called from another suspend function (or a coroutine builder). Scenario blocks are already suspend, so installFor(booking) is a direct call. 

suspend fun installFor(booking: Booking, testId: String, …) {
    for (stub in selected) {
        installStub(stub, testId)     // also suspend; looks synchronous
    }
}
CompletableFuture<Void> installFor(Booking booking, String testId) {
    return selectedStubs(booking).stream()
        .reduce(CompletableFuture.completedFuture(null),
            (acc, stub) -> acc.thenCompose(v -> installStub(stub, testId)),
            (a, b) -> a.thenCompose(v -> b));
}

internal

package-private, but for the whole compiled module

MockInstaller and scopedTo are internal: visible anywhere in this module, invisible outside it. Journeys never construct a MockInstaller — JourneySpec does that per scenario, with the evidence sink already wired. Provisioning constructs one without a sink. Making the installer public would invite a second install path that skipped leftover checks or ownership.
