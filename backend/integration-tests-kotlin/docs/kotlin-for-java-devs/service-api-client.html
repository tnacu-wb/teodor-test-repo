Inside ServiceApiClient

Why every typed client sends requests through one class, how to write a new client in five lines per endpoint, and a plain-Java explanation of each Kotlin keyword that makes it work. No Kotlin experience assumed.

1Why this class exists

Every integration test calls a real service. Each call must do three things the same way, every time:

  • Send the baggage header with the scenario's wb-test-id. WireMock stubs match on this member. A request without it misses every stub that belongs to your test — or worse, silently consumes another running test's stub.
  • Send and accept JSON.
  • Decode the response into ApiResult<T>, which keeps the raw response, the raw body text, the decoded success body, and the decoded error body together.

We used to repeat those steps by hand in every client method — about six lines of ceremony, thirty times over. Forgetting one line compiled fine and failed at runtime, confusingly. ServiceApiClient ends that: it is the only way a client sends a request, and it supplies the whole frame itself.

suppliedGET {baseUrl}/ohip/ratePlans
suppliedAccept: application/json
suppliedbaggage: wb-test-id=<testId>[, wb-feature-overrides=…]
you writeparameter("hotelId", hotelId) ← only the endpoint-specific part
suppliedresponse → ApiResult<RatePlansResponse>

The design goal was stronger than "less duplication": the two historical mistakes are now impossible to write. You cannot forget testId, because it is a required parameter of every request verb. You cannot forget ApiResult, because it is the verbs' return type.

2Writing a client

A client class holds one ServiceApiClient and one method per endpoint. The constructor default calls IntegrationTestConfig.serviceApiClient(baseUrl), which wires the shared evidence-capturing HTTP client, so journeys just write OhipApi().

clients/ohip/OhipApi.kt 
class OhipApi(
    private val http: ServiceApiClient =
        IntegrationTestConfig.serviceApiClient(IntegrationTestConfig.config.ohipInterfaceBaseUrl),
) {
    suspend fun getRatePlans(
        hotelId: String,
        testId: String,
    ): ApiResult<RatePlansResponse> =
        http.get("/ohip/ratePlans", testId) {
            parameter("hotelId", hotelId)
        }
}
// The pre-refactor version of the same method. Every client method
// repeated this frame; each line was forgettable.
suspend fun getRatePlans(hotelId: String, testId: String): ApiResult<RatePlansResponse> {
    val response =
        client.get("$baseUrl/ohip/ratePlans") {
            accept(ContentType.Application.Json)      // forgettable
            parameter("hotelId", hotelId)
            headers.append(BAGGAGE_HEADER, scenarioBaggage(testId))  // forgettable, breaks stub matching
        }
    return response.toApiResult(json)               // forgettable
}

The four verbs cover every current endpoint shape:

VerbUse forExample
getJSON GEThttp.get("/v1/companies/$id", testId)
postJSON POST with a bodyhttp.post("/v1/reservations", request, testId)
putJSON PUT with a bodyhttp.put("/v1/reservations/ancillaries", request, testId)
getTextSuccess body kept as raw texthttp.getText("/v1/companies/id/$id", testId)

All verbs take an optional featureFlagOverrides map (encoded into the baggage header) and an optional trailing block for endpoint specifics: query parameters via parameter(...), extra headers via header(...). SpendingApi uses the block for its WB-Authorization header, for example.

3The rules that protect it

Two hermetic architecture tests in LayerDependencyRulesTest run on every ./gradlew test, no Docker needed:

  • Every public client method takes testId. A method without it fails the build by name. The check is a substring match on methods that declare an explicit return type.
  • Clients import only from an allowlist. The allowed Ktor imports are parameter and header. Everything else a client needs — ServiceApiClient, ApiResult, IntegrationTestConfig, models — is named in that same list. A new import prefix fails the build, naming the file and the import. That is how a raw request verb, setBody, or ContentType is kept out: they are not on the list.

Known limit: the rules read import statements as text. A fully qualified inline call would slip past them. That is a declared limitation of the whole rule family, not a loophole to use.

4Kotlin, feature by feature

ServiceApiClient is about 120 lines but uses most of Kotlin's function-level keywords. Each card below explains one feature: what it is, the nearest Java concept, and — expand the panel — what the code would look like without it. Toggle any code panel between Kotlin and the Java equivalent.

val constructor properties

a record, or final fields + constructor + getters

Kotlin merges field, constructor parameter, assignment, and getter into one declaration in the class header. val means final; var would mean mutable. There is no separate constructor body to write. 

class ServiceApiClient(
    @PublishedApi internal val baseUrl: String,
    @PublishedApi internal val client: HttpClient,
)
public final class ServiceApiClient {
    private final String baseUrl;
    private final HttpClient client;

    public ServiceApiClient(String baseUrl, HttpClient client) {
        this.baseUrl = baseUrl;
        this.client = client;
    }
    // + two getters
}

= default default arguments

telescoping constructors, or a builder

A parameter can declare its own default value. Callers omit it; there is no overload explosion. This is why journeys can write OhipApi() — the typed client's constructor defaults its ServiceApiClient through the factory — while a unit test can still inject a mock-engine transport, and why every verb call can skip featureFlagOverrides and the trailing block when it has none. Decoding is not a constructor default: every verb calls toApiResult(ServiceJson) (or toTextApiResult(ServiceJson)) so encode and decode cannot silently diverge. 

class OhipApi(
    private val http: ServiceApiClient =
        IntegrationTestConfig.serviceApiClient(…),
)

suspend inline fun <reified T : Any> get(
    path: String,
    testId: String,
    featureFlagOverrides: Map<out BaggageFlag, Boolean> = emptyMap(),
    crossinline block: HttpRequestBuilder.() -> Unit = {},
): ApiResult<T>

// call sites — all valid:
OhipApi()                                      // journeys
OhipApi(ServiceApiClient(url, mockEngineClient))  // a unit test's transport
http.get("/ohip/ratePlans", testId)            // skip flags and block
// Java needs one constructor per shape, delegating down:
public OhipApi() {
    this(IntegrationTestConfig.serviceApiClient(IntegrationTestConfig.config.ohipInterfaceBaseUrl));
}

= body expression bodies & string templates

arrow-like shorthand Java methods don't have; String.format / +

When a function is one expression, fun f(...): T = expression replaces the { return ...; } block. Every migrated client method uses this — the whole method is a single call to a verb. Inside strings, "$baseUrl$path" and "${request.hotelId}" splice values directly: Kotlin's version of concatenation, checked by the compiler.

T.() -> Unit lambdas with receiver & trailing lambdas

Consumer<T>, but this becomes the T inside

The verbs' last parameter is block: HttpRequestBuilder.() -> Unit. Read the type as: "a function that runs as if it were a method of HttpRequestBuilder". Inside the lambda, this is the request builder, so you write parameter("hotelId", hotelId) bare — no b -> b. prefix. And when a lambda is the last argument, Kotlin lets it move outside the parentheses, which is why a call reads like a configuration block. 

// these two calls are identical; the second is the idiomatic form
http.get("/ohip/ratePlans", testId, emptyMap(), { parameter("hotelId", hotelId) })

http.get("/ohip/ratePlans", testId) {
    parameter("hotelId", hotelId)      // 'this' is the HttpRequestBuilder
}
// Java's closest shape — note the explicit receiver variable:
http.get("/ohip/ratePlans", testId, Map.of(), builder -> {
    builder.parameter("hotelId", hotelId);
});
Why do we need it here?

It is the escape hatch that keeps ServiceApiClient from needing a parameter for every possible request feature. The verbs own the invariant part (baggage, JSON, decoding); the block hands you the builder for the variable part (query parameters, the odd extra header). Without it, every new endpoint quirk would grow the verb signatures.

suspend coroutines

CompletableFuture / virtual threads, with blocking-style syntax

suspend marks a function that can pause at I/O — here, the HTTP call — without blocking a thread. The code still reads top to bottom like blocking code; the compiler does the continuation plumbing that Java expresses with thenCompose chains. One rule matters day to day: a suspend function can only be called from another suspend function (or a coroutine builder). Kotest test bodies are already suspend, so journeys just call client methods directly. 

suspend fun getRatePlans(hotelId: String, testId: String): ApiResult<RatePlansResponse> =
    http.get("/ohip/ratePlans", testId) { parameter("hotelId", hotelId) }

// caller (a journey): looks fully synchronous
val result = OhipApi().getRatePlans(hotelId, testId)
// the async-Java shape this replaces:
CompletableFuture<ApiResult<RatePlansResponse>> getRatePlans(String hotelId, String testId) {
    return client.getAsync(url)
        .thenCompose(response -> decode(response));
}
// caller must join() or keep chaining

inline + reified T

what removes Jackson's readValue(json, MyDto.class) token

Java generics are erased: inside a method you cannot ask "what is T?", which is why Java JSON APIs make you pass a Class<T>. Kotlin has the same erasure — unless the function is inline. Then the compiler copies the function body into each call site, where the concrete type is known, and reified T lets the body use it. Best of all, T is inferred from the client method's declared return type. This single feature is why client methods can be one expression with no class tokens anywhere. 

suspend inline fun <reified T : Any> get(path: String, testId: String, …): ApiResult<T>

// caller — T = RatePlansResponse is inferred from the return type:
suspend fun getRatePlans(…): ApiResult<RatePlansResponse> =
    http.get("/ohip/ratePlans", testId) { … }
// erased generics force an explicit token, Jackson-style:
public <T> ApiResult<T> get(String path, String testId, Class<T> type) { … }

// every caller repeats the type twice:
ApiResult<RatePlansResponse> result =
    http.get("/ohip/ratePlans", testId, RatePlansResponse.class);
What would the code look like without it?

Every one of the ~30 client methods would pass a class token (or a serializer) explicitly, exactly like the Java tab above. Compare getText in the real file: its type is fixed at ApiResult<String>, so it needs none of this — no inline, no reified. Reading get and getText side by side shows that the whole keyword pile-up exists to serve reified.

crossinline

no equivalent — a compiler-demanded restriction

A consequence of inline, not a choice. Inlined lambdas normally allow a bare return that exits the calling function. Our block is not called directly — it is passed into Ktor's own builder lambda — and from that nested context such a return would be meaningless. crossinline declares "this lambda is called from a nested context; forbid non-local returns in it". You never plan for it; the compiler error tells you when it is required.

@PublishedApi internal

module-wide package-private, made visible to inlined code

Two things at once. internal is a visibility Java lacks: visible anywhere in this compiled module, invisible outside it — package-private, but for the whole module. Then the wrinkle: an inline function's body is copied into callers' classes, so everything it touches must be visible from there — a public inline function may not read private fields. @PublishedApi internal is the sanctioned middle ground: hidden from humans outside the class, but reachable by inlined code.

What breaks without it?

Mark client or baseUrl as private and the file stops compiling: "public-API inline function cannot access non-public-API property". The same rule applies to scenarioDefaults, which the verbs call and which is therefore also @PublishedApi internal. Mark them plain public and it compiles, but the class grows public surface that invites http.client.get(...) bypasses. The annotation keeps the narrow waist narrow.

?. let null-safe calls

if (x != null) { … }, checked by the compiler

Not in ServiceApiClient itself, but all over its callers. String? is a type that admits null; plain String does not, and the compiler enforces the difference. x?.let { ... } means "if x is not null, run the block with it". Clients use it for optional query parameters: 

country?.let { parameter("country", it) }   // 'it' is the unwrapped non-null value
if (country != null) {
    builder.parameter("country", country);
}
