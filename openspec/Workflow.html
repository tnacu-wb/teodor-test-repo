Overview

What is OpenSpec?

OpenSpec is a lightweight, configurable framework for writing and managing software specifications. You and your coding agent agree on what to build before any code is written, then the agent builds it, checks it against the spec, and records the result as the new source of truth.

See the workflow → openspec.dev ↗ Docs ↗ GitHub ↗
The spec framework for building the right thing and building it right. openspec.dev

Three ideas to hold on to.

Everything else in this guide builds on these.

spec

Living specs are the truth

Each capability has a spec.md (what must happen) and a design.md (how it actually works) under openspec/specs/. Agents read them before touching code.

change

Work happens in changes

Every piece of work gets a folder in openspec/changes/ with a proposal, delta specs, a design and tasks. It is reviewed before code, and merged into the living specs when done.

skill

Skills drive the agent

You move a change forward by running a skill such as /openspec-propose or /openspec-apply-change. Our config.yaml adds house rules to every one.

1Agents stop guessing: requirements, edge cases and scenarios are written down before implementation.
2One contract per capability covers backend, web, iOS, Android and GraphQL.
3You review a short plan instead of a large diff, and catch wrong assumptions early.
4Archive keeps the living specs in step with the code, so the next change starts from the truth.

Install and set up.

OpenSpec is already configured in this repository. You only need the CLI on your machine and the skills generated for your AI tool.

Check Node.js

OpenSpec needs Node.js 20.19.0 or newer.

$node --version

Install the CLI

Install globally with npm. On macOS, Homebrew also works and brings Node with it.

$npm install -g @fission-ai/openspec@latest
$brew install openspec

Verify

Confirms the CLI is on your PATH. This repository's skills were generated with 1.12.0.

$openspec --version

Generate the skills for your tools

From the repository root, generate the 12 OpenSpec skills for Claude Code and Kiro. The existing openspec/config.yaml and specs are left untouched.

$openspec init --tools claude,kiro
Creates .claude/skills/openspec-* and .kiro/skills/openspec-*. Restart your IDE or agent session so it picks them up.

Check it resolves this repository

root.path should be the repository root, not a nested folder. You're ready: open the Workflow tab.

$openspec list --json
Upgrading later? Update the CLI with the same install command (or brew upgrade openspec), then run openspec update from the repository root to refresh the generated skills.

Which way in?

Pick the route that matches where you are. Every route ends at the same place: archive, which merges your change into the living library.

Not sure yet?

Think it through

Want to review each step?

Guided route

Create the change, then write one artifact per run so you can read and correct each before the next.

Every stop, in order.

What to type, what happens, and what you get. In Claude Code, type the skill as a slash command; in Kiro, name the skill or describe the action in plain words. The change name is optional once one change is active.

00Optional

Explore the problem

A thinking partner. It reads code and existing specs, maps the problem, and helps you decide. It never writes product code.

>/openspec-explore how does card payment expiry work?

Use it when

  • The problem or desired behaviour is unclear
  • You need to trace an existing code path
  • Implementation discovery challenges the plan

Produces

A clearer picture. No files.

01Plan

Start the change

Creates the change folder and shows the proposal instructions. It does not write any artifact yet.

>/openspec-new-change add-payment-refund-reason

Name it in kebab-case, verb first: add-…, fix-…, update-….

Creates

changes/<name>/.openspec.yaml

Next

Run continue-change to write the proposal.

02Plan · continue ①

Write the proposal

The why and the scope. The agent asks once for Jira, Figma, Confluence and design docs, reads what it can reach, and finds the affected capabilities.

>/openspec-continue-change

Produces

proposal.md

Inside it

  • Requesting squad, references, capability impact table
  • ## Cross-squad work if another squad's backend code must change
  • ## Conflicts and decisions when sources disagree
03Plan · continue ②

Write the delta specs

What the system must do, as requirements and WHEN/THEN scenarios. Observable behaviour only, no classes or frameworks. Behaviour-changing blocking decisions get settled here.

>/openspec-continue-change

Skipped automatically when the proposal sets skip_specs: true (refactors, logging, tooling).

Produces

specs/<domain>/<subdomain>/<capability>/spec.md

Uses

  • ADDED / MODIFIED / REMOVED / RENAMED requirement blocks
  • ## Purpose only for a new capability
04Plan · continue ③

Write the change design

How it will be built. Remaining blocking decisions are resolved here, asking you when needed. Short is fine when nothing architectural changes.

>/openspec-continue-change

Produces

design.md

Ends with

  • ## Living design reconciliation: what archive must carry into the living design
05Plan · continue ④

Write the tasks

A checklist of small, verifiable tasks in dependency order. Each one names the area, the outcome, and how to check it.

>/openspec-continue-change
Stops and sends you back to design if any blocking decision is still open.

Produces

tasks.md

Watch for

  • Another squad's backend work sits in its own group, labelled as a handoff
  • Investigations become spike tasks with a decision outcome
⚡

Express: stops 02–05 in one run

Same rules, same four files, no pause between them. Use propose to create a change and plan it in one go, or ff-change to fast-forward a change you already started.

>/openspec-propose add-payment-refund-reason
>/openspec-ff-change
06Build

Implement the tasks

Works through tasks.md in order and ticks a task only after its stated check passes. Pauses on blockers.

>/openspec-apply-change
Never edits the living spec.md or design.md. Those change only at archive.

07Optional early check

Verify code against the plan

Compares the implementation with the change's tasks, specs and design. Archive runs this for you, so running it yourself just finds problems sooner.

>/openspec-verify-change

Reports

  • CRITICAL: must fix before archive
  • WARNING: should fix
  • SUGGESTION: nice to fix
08Finish

Archive into the living library

Promotes delivered reality. Your change becomes the new truth for its capability.

>/openspec-archive-change add-payment-refund-reason
  1. Runs verify-change. Stops on CRITICAL, asks you about WARNINGs.
  2. Runs strict validation on the change.
  3. Syncs delta specs into the living spec.md.
  4. Writes or updates the living design.md from the reconciliation section.
  5. Only then moves the change to changes/archive/.

Updates

specs/…/spec.mdspecs/…/design.mdchanges/archive/<date>-<name>/

Code differs from the spec?

  • Needs a decision: owned open question in the living design
  • Plain bug: issue tracker
  • Code is deliberate: fix the spec through a new change

Your files live in two places.

The change folder is the plan for one piece of work. The living library is what is true right now. Only archive moves anything from one to the other.

Change workspace

openspec/changes/<change-name>/

proposal.md why and scope
specs/…/spec.md behaviour delta
design.md how this change is built
tasks.md implementation checklist
→
archive

Living library

openspec/specs/<domain>/<subdomain>/<capability>/

spec.md what must happen (the contract)
design.md what does happen (architecture, defaults, open questions)

Command reference

Every skill, explained.

What each skill is for, when to reach for it, what it changes, and a sentence you can say instead of the command.

openspec-explorePlan · optional

Think before you plan.

When
The problem is unclear, you need to trace code, or discovery mid-build challenges the plan.
Does
Reads code, specs and the active change; maps the problem; helps you decide.
Changes
Nothing. No product code, no artifacts.

Or say: “Let's explore how payment expiry works before we plan anything.”

openspec-new-changePlan

Open a new change folder.

When
You want the guided route and to review each artifact in turn.
Does
Creates changes/<name>/ and shows the proposal instructions, then stops.
Changes
Only the empty change scaffold. No proposal yet.

Or say: “Start a new OpenSpec change called add-payment-refund-reason.”

openspec-continue-changePlan

Write the next artifact. Just one.

When
After new-change, four times: proposal, specs, design, tasks.
Does
Picks the first ready artifact, reads what came before, applies config.yaml rules, writes the file, stops.
Changes
One of proposal.md, delta specs, design.md, tasks.md.

Or say: “Continue the change and write the next artifact.”

openspec-proposePlan · express

Create and fully plan a change in one run.

When
Scope and expected behaviour are already clear.
Does
Creates the change, then writes proposal, specs, design and tasks back to back. Stops before any code.
Changes
The whole change folder.

Or say: “Propose a change to add a refund reason to the refund status API.”

openspec-ff-changePlan · express

Fast-forward a change you already started.

When
You created the change (or wrote the proposal) and want the rest of the plan at once.
Does
Writes every remaining planning artifact without pausing.
Changes
The missing artifacts in the change folder.

Or say: “Fast-forward this change to tasks.”

openspec-apply-changeBuild

Build it, task by task.

When
Planning is complete, or to resume implementation.
Does
Implements tasks in order and ticks each only after its check passes. Pauses on blockers.
Changes
Product code and checkboxes in tasks.md. Never the living files.

Or say: “Apply the change” or “Continue implementing.”

openspec-update-changeBuild · if needed

Change the plan, keep it coherent.

When
A decision or discovery materially changes scope, behaviour, architecture or order.
Does
Revises the affected planning artifacts and keeps them consistent with each other.
Changes
Proposal, specs, design or tasks. Never code.

Or say: “Update the change: the refund reason is now optional.”

openspec-verify-changeFinish

Does the code match the plan?

When
Any time after apply. Archive runs it automatically.
Does
Checks completeness, correctness against specs and scenarios, and coherence with the design.
Changes
Nothing. Reports CRITICAL, WARNING and SUGGESTION findings.

Or say: “Verify the change against the implementation.”

openspec-archive-changeFinish

Make the change the new truth.

When
Tasks are done and the code is merged or ready.
Does
Verify → strict validation → sync specs → write living design → move to archive.
Changes
Living spec.md and design.md; moves the change to changes/archive/.

Or say: “Archive the change.”

openspec-bulk-archive-changeFinish

Archive several finished changes at once.

When
Multiple parallel changes are complete.
Does
Runs the archive flow for each selected change.
Changes
Living files for every affected capability.

Or say: “Archive all completed changes.”

openspec-sync-specsUtility

Merge delta specs without archiving.

When
Rarely. Archive already syncs, and also writes the living design.
Does
Merges the change's delta specs into the living spec.md files.
Changes
Living spec.md only. The living design is not reconciled.

Or say: “Sync this change's specs into the main specs.”

openspec-onboardUtility

Learn by doing, with narration.

When
You are new to OpenSpec.
Does
Walks a full workflow cycle on real code, explaining each step.
Changes
Whatever the practice change touches.

Or say: “Onboard me to OpenSpec.”

The skills call these for you. Run them yourself to look around or check your work.

CommandWhat it tells you

openspec status --change <name>Which artifacts are done, ready or blocked.
openspec show <name>A change or spec, rendered.

From openspec/config.yaml

House rules the agent follows.

OpenSpec skills drive the workflow. Our config.yaml adds these rules to every stop, so you don't have to repeat them in prompts.

⌂

Capabilities live under product domains

Specs are organised by product domain, not by app or folder. A subdomain groups related capabilities. Reuse an existing one; propose a new one only with a reason.

book-pay/payment/new-card-payment
book-paymanage-modifydiscover-searcharrive-stay-leaveidentity
=

One contract, every surface

Never write separate specs for backend, web, Android, iOS or GraphQL. One capability describes shared behaviour; platform detail goes in only when it is observable.

⇄

Cross-squad work is called out

backend/<squad>/ belongs to that squad. If your change needs another squad's backend code, it must be explicit:

  • Proposal: ## Cross-squad work
  • Design: owning squad per service
  • Tasks: its own labelled handoff group
?

References: asked once

Before the proposal, the agent asks once for Jira, Figma, Confluence and design docs. “Not provided” is fine. It never invents links or guesses at content it can't read.

⚖

Proportionate, not ceremonial

Sections that don't apply are left out. A design can be two lines when nothing architectural changes. No invented migration plans, diagrams or rollout work.

!

Conflicts are classified, never silently resolved

When sources disagree, the proposal records it under ## Conflicts and decisions with an owner. Each type is handled at a fixed stop:

Blocking decisionResolved at specs (if it changes behaviour) or design. Tasks stop if any remain.
Implementation investigationBecomes a spike task with a decision outcome.
Bounded accepted unknownMay remain, with an owner and a reason it's safe to ship.
Unrelated future questionLeft out of the tasks.
◎

Where does each kind of truth go?

The living library keeps intent and reality apart, so neither hides the other.

spec.mdWhat should happen. The contract. Changes only through a change.
design.mdWhat does happen. Architecture, flags, defaults, failure paths.
Open questionsWhere code and contract differ and someone must decide. Always owned.
Issue trackerPlain defects with an obvious fix. Not recorded in the design.
