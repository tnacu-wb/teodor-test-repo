# Requirements Document

## Introduction

The Kotlin integration test framework (`backend/integration-tests-kotlin/`) currently provides two test base classes for authors: `SingleActionSpec` (a `BehaviorSpec` with a `When`/`Then` structure for single-action tests) and `JourneySpec` (a `FeatureSpec` with a `scenario` structure for multi-step business journeys). Maintaining two base classes adds conceptual overhead, and the framework is standardising on `JourneySpec` as the single authoring entry point (continuing the migration begun in CTECH-10368).

This work migrates every remaining test that extends `SingleActionSpec` to `JourneySpec`, removes the `SingleActionSpec` base class, and updates all references and documentation so the framework exposes exactly one base spec. Test coverage and observable assertions must be preserved exactly — this is a structural refactor, not a behavioural change.

## Glossary

- **SingleActionSpec**: The `BehaviorSpec`-based base class at `testkit/SingleActionSpec.kt` that exposes a `When(name) { ... Then(name) { ... } }` structure plus `booking`, `testId`, `mocks`, `expect`, and `attachEvidence`.
- **JourneySpec**: The `FeatureSpec`-based base class at `testkit/JourneySpec.kt` that exposes a `scenario(name) { ... }` structure plus the same `booking`, `testId`, `mocks`, `expect`, and `attachEvidence` helpers.
- **Reservation_Spec**: A test class in `journeys/reservation/` that currently extends `SingleActionSpec`.
- **Migration**: Changing a Reservation_Spec to extend `JourneySpec`, converting its `When`/`Then` blocks into a single `scenario` block, while preserving all `mocks.installFor(...)`, client calls, `expect(...)` assertions, and `attachEvidence(...)` calls unchanged.
- **Test_ID**: The unique `x-amzn-trace-id` correlation identifier generated by the base spec; both base classes generate it identically.
- **Module**: The `backend/integration-tests-kotlin/` Gradle module.

## Assumptions

- `JourneySpec` and `SingleActionSpec` expose identical author-facing members (`booking`, `testId`, `mocks`, `expect`, `attachEvidence`), confirmed by reading both classes, so migration requires no helper changes.
- The only structural difference is `When`/`Then` (BehaviorSpec) versus `scenario` (FeatureSpec); a `When` containing one or more `Then` blocks maps to a single `scenario`, as established by the CTECH-10368 refactor of `GetFooterBusinessBookerEnGbSpec`.
- All `SingleActionSpec` usages are the 10 reservation specs in `journeys/reservation/`; the two `framework/` references are documentation comments only.
- No other module depends on `SingleActionSpec` (it lives in `src/test`).

## Requirements

### Requirement 1: Migrate Reservation Specs to JourneySpec

**User Story:** As a test author, I want every reservation test to extend `JourneySpec`, so that there is a single, consistent base spec for all integration tests.

#### Acceptance Criteria

1. THE Module SHALL migrate each of the following Reservation_Spec classes from `SingleActionSpec` to `JourneySpec`: `CreateOnHoldHappyPathSpec`, `SingleRoomWithPackagesSpec`, `SingleRoomSingleOccupancySpec`, `SingleRoomNonrefundNoPackagesSpec`, `MultiRoomReservationSpec`, `CreateOnHoldInvalidRateInfoSpec`, `CreateOnHoldSkipRateInfoSpec`, `ReservationErrorMissingRateInfoSpec`, `ReservationErrorOpera500Spec`, and `ReservationErrorUnknownHotelSpec`.
2. WHEN a Reservation_Spec is migrated, THE Module SHALL replace the `import ...testkit.SingleActionSpec` statement with `import ...testkit.JourneySpec` and change the class's superclass from `SingleActionSpec` to `JourneySpec`.
3. WHEN a Reservation_Spec is migrated, THE Module SHALL convert each `When(name) { ... }` block into a `scenario(name) { ... }` block.
4. WHEN a migrated `When` block contains a `Then(name) { ... }` block, THE Module SHALL inline the `Then` body directly into the `scenario` block without introducing a nested `Then` scope.
5. WHEN a Reservation_Spec is migrated, THE Module SHALL preserve unchanged its `Booking` scenario data, its `mocks.installFor(...)` / `mocks.installWith...(...)` calls, its client request construction, every `expect(name) { ... }` assertion, and every `attachEvidence(...)` call.
6. THE Module SHALL NOT change the `description` string, hotel data, rates, packages, dates, or expected status codes and error codes of any migrated Reservation_Spec.

### Requirement 2: Remove the SingleActionSpec Base Class

**User Story:** As a framework maintainer, I want the `SingleActionSpec` class deleted, so that the framework exposes exactly one base spec and authors cannot extend the removed one.

#### Acceptance Criteria

1. WHEN all Reservation_Spec classes have been migrated, THE Module SHALL delete the file `testkit/SingleActionSpec.kt`.
2. AFTER deletion, THE Module SHALL contain no remaining source reference to the `SingleActionSpec` type in `src/test`.
3. IF any remaining file imports or extends `SingleActionSpec` after migration, THEN the deletion SHALL NOT proceed until that reference is removed.

### Requirement 3: Update Framework References and Documentation

**User Story:** As a developer reading the framework, I want all references to `SingleActionSpec` updated, so that comments and docs accurately describe the single-base-spec model.

#### Acceptance Criteria

1. THE Module SHALL update the comment in `framework/config/IntegrationTestConfig.kt` that names `SingleActionSpec` so it no longer references the removed class.
2. THE Module SHALL update the comment in `framework/wiremock/StubLifecycleExtension.kt` that names `SingleActionSpec` so it no longer references the removed class.
3. THE Module SHALL update `docs/README.md` to remove the `SingleActionSpec` usage example and guidance from the "Base Spec Types" section, leaving `JourneySpec` documented as the base spec for test authors.
4. WHEN the documentation is updated, THE Module SHALL retain accurate descriptions of the shared author-facing members (`booking`, `testId`, `mocks`, `expect`, `attachEvidence`).

### Requirement 4: Preserve Test Behaviour and Build Health

**User Story:** As a developer, I want the test suite to compile and behave exactly as before, so that I can trust the refactor introduced no regressions.

#### Acceptance Criteria

1. WHEN the Module is compiled after migration, THE Module SHALL compile successfully with no unresolved references to `SingleActionSpec`.
2. THE migrated test suite SHALL contain the same number of executable test cases, with the same assertions, as before the migration.
3. WHEN the migrated tests are executed against a running integration environment, THE result of each migrated Reservation_Spec SHALL match its pre-migration result (same status codes, error codes, and evidence).

#### Edge Cases

- WHEN a Reservation_Spec declares local helper values (for example `familyBooking` in `MultiRoomReservationSpec` or `reservationApi`/`basketApi`) inside the spec body, THE Module SHALL preserve those declarations at an equivalent scope within the migrated `scenario` structure.
- WHEN a Reservation_Spec uses a specialised installer such as `installWithInvalidRateInfo`, `installWithReservationFailure`, or `installWithoutHotelStubs`, THE Module SHALL keep that installer call unchanged.

## Out of Scope

- Changing assertion logic, scenario data, or expected service responses of any test.
- Renaming the migrated spec files or moving them out of `journeys/reservation/`.
- Modifying `JourneySpec` itself or the mock/stub framework.
- Adding new test coverage.

## Resolved Decisions

- **Spec naming:** Migrated specs keep their current file and class names (no `Spec` suffix dropped, no journey-convention rename). Only the superclass and `When`/`Then` → `scenario` structure change.
